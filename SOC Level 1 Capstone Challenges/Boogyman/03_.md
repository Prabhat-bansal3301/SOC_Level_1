# Boogeyman 3 – Full Attack Chain Investigation in Elastic (Phishing to Domain Compromise)

**Scenario:** the threat group "Boogeyman" returns to attack Quick Logistics LLC. This time the target was the **CEO**. The attacker used an already-compromised employee mailbox to send him a phishing email. He opened the attachment, saw nothing happen and reported it. The security team then found the attachment in his Downloads folder, along with an **ISO** containing a file. The incident window was **29 to 30 August 2023**.

The job is to trace the whole intrusion in **Elastic (Kibana)**: initial execution, persistence, C2, privilege escalation, credential theft, lateral movement, domain controller compromise, and an attempted ransomware deployment.

## Setup in Kibana

- Set the **time filter to the incident dates** (29 to 30 August 2023). Without this you'll see nothing or the wrong data
- Turn **KQL off** to use the plain keyword search. This makes wildcard and simple text searches behave as expected
- Click fields in the left panel to add them as **columns**. The most useful ones here are the process command line, process ID, hostname and event code
- **Sort by `@timestamp` ascending** so events read in the order they happened. This is essential for following an attack

## Attack Flow

```text
Phishing email with ISO attachment (appears as a PDF)
        |
Stage 1 payload runs, copies review.dat to the Temp folder (xcopy)
        |
rundll32 runs the DLL (DllRegisterServer), scheduled task "Review" created
        |
C2 connection (Sysmon Event 3)
        |
Local admin discovered, UAC bypass with fodhelper.exe
        |
Mimikatz downloaded from GitHub, credentials dumped
        |
Pass-the-hash to a second account, share enumeration, credentials found in a script
        |
Lateral movement over WinRM to a second workstation
        |
Mimikatz again, administrator hash passed to reach the domain controller
        |
DCSync attack, then ransomware binary download attempt
```

## Stage 1: Initial Execution and Persistence

**Finding the first process.** Search for the attachment's file name and for `.html` files, since an ISO or disguised document can launch an HTML or script component. A query such as `ProjectFinancialSummary_Q3.pdf*` brings up every event that mentions the malicious attachment. In the results, the **process command line** shows what executed the payload and the **process ID** identifies the process that ran it.

**Implanting a file.** After the first payload ran, a new process copied a file named `review.dat` from the mounted ISO (drive `D:`) into the user's **Temp** folder:

```
xcopy.exe /s /i /e /h D:\review.dat C:\Users\<user>\AppData\Local\Temp\review.dat
```

The xcopy switches are worth knowing: `/s` copies subdirectories, `/i` treats the destination as a folder, `/e` includes empty folders, and `/h` includes hidden files. Using a built-in tool to move the payload is a **living off the land** technique, which blends in with normal activity.

**Executing the implant.** The attacker then ran the file through `rundll32.exe`:

```
rundll32.exe D:\review.dat,DllRegisterServer
```

`review.dat` is really a **DLL** with a misleading extension. `rundll32` runs an exported function from a DLL, and **`DllRegisterServer`** is the standard export Windows calls when registering a DLL. Attackers reuse it as an easy entry point. This is **proxy execution** through a trusted Windows binary.

**Persistence.** A PowerShell command created a **scheduled task named `Review`** that runs the DLL again later. This means the malware survives a reboot or a logoff, so closing the document wouldn't have removed it.

## Stage 2: Command and Control

After the DLL ran, it reached out to the attacker's server. To find it, filter for **Sysmon Event ID 3 (network connection)** and show the destination IP and port columns. The connection went to an external IP on port **80**.

Port 80 (plain HTTP) is a common choice for C2 because outbound web traffic is almost always allowed through firewalls and looks ordinary.

## Stage 3: Discovery and Privilege Escalation

Sorting by time and following the attacker's commands shows a clear pattern:

1. The attacker **enumerated users and groups** on the machine (commands like `whoami` and group listings)
2. He discovered the current account was a **local administrator**
3. A local admin in a standard session still runs with a **filtered token**, so many actions trigger a **UAC prompt**
4. He bypassed it with **`fodhelper.exe`**

**About the fodhelper UAC bypass:**
- `fodhelper.exe` is a trusted Windows binary that **auto-elevates** (runs with high privileges with no prompt)
- When it starts, it reads a registry setting the **current user** can change
- The attacker writes his own command into that registry location, then runs `fodhelper.exe`, which then runs his command **with elevated rights**
- It's a good example of why you should search for registry writes followed immediately by `fodhelper.exe` execution

## Stage 4: Credential Dumping with Mimikatz

With high privileges, the attacker wanted credentials. Filtering for the keyword **`github`** with **Event ID 1 (process creation)** showed a download command fetching a ZIP from a public GitHub release page, saved locally as **`mimi.zip`**. The tool inside is **Mimikatz**, a well-known credential theft tool.

**What Mimikatz does here:**
- It reads credentials from the memory of the Windows login process (LSASS)
- A typical command is `sekurlsa::logonpasswords`, which lists accounts with password hashes
- It can also **pass the hash** (`sekurlsa::pth`): start a process as another user using only that user's hash, with no password needed

Searching for the keyword `mimi*` then shows every command run with the tool. The attacker dumped the logon credentials and then used a **pass-the-hash** to run commands as a second, more privileged account.

## Stage 5: Share Enumeration and More Credentials

Using the new account, the attacker ran a PowerShell script designed to **find network file shares**. It found a share and he **read a script file** stored there. That file contained **hardcoded credentials** for another user.

This is a very common real-world mistake: automation scripts with plaintext passwords stored on shared folders. The attacker simply read the file and took the credentials.

## Stage 6: Lateral Movement to a Second Workstation

With the new credentials, the attacker ran commands **remotely on a second workstation**. The command used a Base64 encoded payload. Decoding it in **CyberChef** (From Base64, then UTF-16LE decoding if the text has gaps between letters) revealed the real command and a domain.

To see what happened on the new host, filter by that hostname and **Event ID 1**. The attacker's command appears as a **child of `wsmprovhost.exe`**. That process is created by **WinRM** (Windows Remote Management), the remote PowerShell service. Seeing it as a parent means someone logged in remotely and ran commands.

## Stage 7: Second Machine and the Domain Controller

On the second workstation the attacker repeated his playbook:
- Downloaded Mimikatz again
- Enumerated the machine
- Dumped credentials, this time getting the **local administrator hash**
- **Passed the administrator hash** to move onto the **domain controller** (the server that holds every account in the company)

## Stage 8: DCSync and Ransomware Attempt

On the domain controller, the attacker ran a **DCSync attack**.

**What is DCSync?** Domain controllers replicate account data to each other. DCSync abuses this: with enough rights, the attacker pretends to be a domain controller and **asks the real one to hand over password hashes** (typically with `lsadump::dcsync /user:<name>`). It doesn't need to touch the DC's disk or LSASS.

He dumped the **Administrator** account and one additional account. Having hashes for key accounts means he could keep access even if passwords change on a single host.

Finally, the attacker tried to download a **ransomware binary** from an external link, the last step before encrypting files. The investigation ends here, which means the attack was caught right before encryption.

A short reference of what to filter on:

| Goal | Filter or field |
|---|---|
| Process creation | Sysmon **Event ID 1** (command line, parent process, host) |
| Network connections (C2) | Sysmon **Event ID 3** (destination IP and port) |
| Follow one attack in order | Sort `@timestamp` ascending |

| Find tool use | Search the keyword (`mimi*`, `github`, the attachment file name) |
| Decode payloads | CyberChef (From Base64) |

## Key Takeaways

- **Read events in time order.** Sorting ascending turns scattered logs into a story with a clear beginning, middle and end
- **Pivot using what you just learned:** a file name leads to a process, a process leads to a command, a command leads to a tool name, and a tool name leads to everything else it ran
- **Built-in tools hide the attack:** `xcopy`, `rundll32`, PowerShell, scheduled tasks and WinRM are all legitimate Windows features
- **`wsmprovhost.exe` as a parent** shows remote WinRM activity on that host
- **Mimikatz usage** (download, `sekurlsa`, pass-the-hash, DCSync) is a strong sign of full domain compromise
- **Hardcoded credentials in scripts and shares** gave the attacker his next step. Never store passwords in plaintext files
- **Defences to remember:**
  - Block ISO and disk-image attachments from email, or warn on them
  - Alert on new scheduled tasks and on `fodhelper.exe` launches
  - Restrict admin accounts and monitor LSASS access
  - Alert on DCSync replication requests coming from non-domain-controller machines
  - Use unique local admin passwords so one hash doesn't unlock many machines
