## Enterprise Network Components — Security Perspective

### Network as an Ecosystem
All components are interconnected — compromise one = potential access to all.
The network perimeter (internal ↔ Internet boundary) is the primary attack surface.

---

### Key Network Components

#### 1. User Workstations (Endpoints)
**What:** Employee PCs and laptops — daily work devices.
**Attack vector:** Phishing emails, malicious downloads.

| Security concern | Monitoring focus |
|-----------------|-----------------|
| Most common entry point for attackers | Endpoint logs → malicious processes |
| Less monitored than servers | Network logs → C2 connections |
| Foothold for lateral movement | EDR alerts, process creation events |

---

#### 2. File & Database Servers
**What:** Store the organization's most valuable data — documents, customer records, HR, financial data.

| Attacker goal | Detection |
|---------------|-----------|
| Ransomware → encrypt file servers | Unusual file modification volume |
| Data exfiltration → steal DB contents | Large outbound transfers |
| Unauthorized DB queries | Database audit logs |

---

#### 3. Application Servers (Web, Email, VPN)
**What:** Externally-facing services employees and customers rely on.

| Type | Security risk |
|------|--------------|
| **Web servers** | SQLi, XSS, RCE exploits |
| **Email servers** | Phishing delivery, credential theft |
| **VPN gateways** | Brute-force, stolen credentials → internal access |

**Monitor for:**
- Exploit attempts (SQLi, directory traversal)
- Brute-force login attempts
- Suspicious external IPs on sensitive apps

---

#### 4. Active Directory (AD) / Authentication Servers
**What:** Identity backbone — manages all users, groups, computers, and access rights.

**Why attackers love AD:**
```
Compromise one domain admin account
    → Control entire enterprise
    → Access all systems, data, and services
```

**Monitor for:**
- Multiple failed logins (password spraying)
- Unusual logins from external IPs or odd hours
- Accounts accessing systems they normally don't

---

#### 5. Routers & Switches (Network Infrastructure)
**What:** Routers connect networks (LAN ↔ Internet); switches connect internal devices.

**If compromised, attackers can:**
- Intercept and manipulate traffic (MITM)
- Create backdoors by rerouting traffic
- Open hidden channels to Internet

---

#### 6. Firewalls / Perimeter Devices
**What:** Primary security gateway between trusted internal network and untrusted Internet.

**Functions:**
- Inspects and filters inbound/outbound packets
- Blocks unauthorized access to internal services (DB, RDP)
- Deep packet inspection, IPS, malware detection

**Logs are often FIRST indicators of:**
```
Port scans → attacker reconnaissance
Brute-force → credential attacks
Exploit attempts → active attack in progress
```

---

### Component Security Priority Matrix

| Component | Attack Target? | Monitoring Priority |
|-----------|---------------|-------------------|
| Endpoints | ✓ (entry point) | High — EDR + network |
| File/DB Servers | ✓ (data) | Critical |
| Web/Email/VPN | ✓ (external facing) | Critical |
| Active Directory | ✓ (identity/privilege) | Critical |
| Routers/Switches | Occasionally | Medium |
| Firewalls | Rarely | High (log analysis) |

---

### Attack Path — Typical Enterprise Breach

```
Phishing → endpoint compromise
    ↓
C2 established → network logs show unusual traffic
    ↓
Lateral movement → AD auth logs show account anomalies
    ↓
Privilege escalation → AD domain admin compromised
    ↓
Data exfiltration → file/DB server + firewall logs show large outbound transfers
```

> Knowing each component's role = knowing where to look when something goes wrong.

# Network Visibility

## Overview
Network visibility is the ability to monitor and understand what's happening across a network. It's a core principle in security analysis — **you can't defend what you can't see**. It underpins threat detection, incident investigation, and overall security posture. The goal isn't to track every single packet, but to have the right tools and logs to build a clear, actionable picture of activity.

Visibility comes from two primary log sources:
- **Host-centric logs**
- **Network-centric logs**

Understanding the difference between them — and how to correlate them — is essential for piecing together an attack timeline.

## Why Visibility Matters

Without visibility, malicious activity (malware infections, unauthorized access, data exfiltration) can go completely unnoticed. Effective visibility enables analysts to:

| Capability | Description |
|---|---|
| **Detect Anomalies** | Spot unusual patterns that could indicate an attack |
| **Investigate Incidents** | Reconstruct the timeline/events of an attack |
| **Hunt for Threats** | Proactively search for hidden adversaries in the network |
| **Ensure Compliance** | Meet regulatory requirements via logging and monitoring |

---

## Host-Centric Logs

Generated by individual devices (hosts) — servers, workstations, laptops. Provide a **ground-level, detailed view** of activity on a specific machine. Essential for understanding the direct impact of an attack on a system.

### Key Sources

- **Operating System Logs**
  - Windows Event Logs, Linux `syslog`, macOS logs
  - Record user logons, process creation, service startups, failed login attempts
- **Application Logs**
  - Logs from software running on the host — web servers (Apache, Nginx), databases (MySQL, MSSQL), etc.
- **Security Tool Logs**
  - Antivirus, EDR (Endpoint Detection and Response) agents, HIDS (Host-based Intrusion Detection Systems)

### What Host Logs Help With
- Tracking **who logged in, when, and with what privileges** — critical for detecting both external attacks and insider threats
- **Malware impact assessment** — confirming execution of a malicious file and identifying changes to the registry, file system, or running services

---

## Network-Centric Logs

Generated by network appliances sitting on the network, monitoring traffic **between devices** (as opposed to activity on a single device).

### What They Show
- Source/destination IPs, ports, protocols
- Action taken (allowed/blocked)
- The "when," "where," and "how" of traffic — recon attempts, lateral movement, exfiltration attempts

### Key Sources

- **Firewalls**
  - Record every connection allowed/denied based on security rules
  - First place to check for unauthorized inbound connection attempts
- **IDS/IPS** (Intrusion Detection/Prevention Systems)
  - Monitor traffic for known attack signatures or anomalous behavior
  - Critical for real-time attack detection
- **Routers/Switches**
  - Don't log traditionally, but generate **flow data** — who talked to whom, for how long, how much data
  - Good for high-level traffic overview
- **Web Proxies**
  - Record every website a user visits
  - Useful for spotting web-based threats, policy violations, data exfiltration
- **VPN**
  - Track who is connecting remotely, from where, and when
  - Essential for monitoring remote access security

### Why Network Logs Matter
- **Early Threat Detection** — catching port scans, brute-force attempts, known-malicious-IP connections at the network edge
- **C2 (Command & Control) Detection** — spotting communication between a compromised internal host and an external attacker server
- **Tracking Lateral Movement** — observing an attacker pivoting between compromised internal machines
- **Detecting Data Exfiltration** — flagging unusually large/suspicious outbound transfers
- **Broad Context** — understanding attack scope by seeing what else a compromised host tried to talk to

---

## Host vs. Network Logs — Analogy

> Host-centric logs tell you **what happened inside a room**.
> Network-centric logs tell you **who entered and left the building**.

To get the complete picture, both sources must be correlated together.

---

# Network Perimeter

**Core idea:** The boundary between your trusted internal network and the untrusted internet. Every attacker starts here — it's the first thing they probe, and the first place a SOC analyst sees trouble.

| Zone | Contains |
|---|---|
| Internal (trusted) | Employee workstations, internal servers, business apps |
| Perimeter | Firewall, router/gateway, DMZ, VPN gateway |
| External (untrusted) | The internet |

---

## Core Components

| Component | Role | Real example |
|---|---|---|
| Firewall | Filters traffic in/out by rule | Blocks inbound traffic on port 3389 (RDP) from the public internet |
| Router/Gateway | Routes traffic, enforces access rules | ACLs restricting which subnets can reach which |
| DMZ | Isolated zone for public-facing services | Public website server lives here — if it's compromised, attacker still can't reach internal AD/DB servers |
| VPN Gateway | Encrypted remote access | Employee connects from home, tunnels into internal LAN securely |

**Why the DMZ specifically matters:** it's a blast-radius containment strategy. Put your public web server in the general internal network and one RCE vulnerability = attacker has a foothold next to your domain controller. Put it in a DMZ and that same RCE only gets them a sandboxed segment with no route to anything sensitive.

---

## Typical Small-Enterprise Layout

Internet → Firewall → DMZ (public web/mail server) → Internal LAN (AD, file server, DB) — no direct internet exposure 
Remote employees → VPN Gateway → Internal LAN


---

## What Goes Wrong (and What Attackers Do)

| Perimeter weakness | Attacker action |
|---|---|
| Exposed RDP/SSH/SMB | Direct exploitation or credential attack |
| Open/unnecessary ports | Reconnaissance (Nmap scans) to map attack surface |
| Weak login on exposed service | Brute-force |
| No egress filtering | Data exfiltration channel |

**Real-world framing:** most breaches you'll read about (e.g. exposed RDP ransomware incidents) trace back to a perimeter misconfiguration, not some 0-day exploit. Misconfig is the actual #1 root cause here, not sophistication.

---

## Analyst's Role at the Perimeter

- Review firewall logs — allowed vs. blocked connections
- Spot scanning/brute-force patterns (many failed attempts, sequential port hits)
- Flag abnormal outbound traffic (possible beaconing/C2 or exfil)
- Maintain awareness of what's *supposed* to be exposed — anything extra is attack surface that shouldn't exist

---

# Monitoring the Perimeter

**Core idea:** Firewalls, IDS/IPS, and access controls don't just block stuff — they generate the evidence trail. Reading that trail correctly is the actual analyst skill.

Monitoring lets you catch:
- Early-stage attacks (port scans, brute-force)
- Misconfigurations exposing services that shouldn't be reachable
- Outbound anomalies (malware, exfiltration)

---

## Scenario 1: Port Scanning

**Firewall log:**

    2025-09-22 08:30:05 BLOCK TCP 203.0.113.10:50001 -> 10.0.0.20:21
    2025-09-22 08:30:06 BLOCK TCP 203.0.113.10:50002 -> 10.0.0.20:22
    2025-09-22 08:30:07 ALLOW TCP 192.0.2.115:51235 -> 10.0.0.50:443
    2025-09-22 08:30:08 BLOCK TCP 203.0.113.10:50003 -> 10.0.0.20:23
    2025-09-22 08:30:11 BLOCK TCP 203.0.113.10:50005 -> 10.0.0.20:53

**Pattern:** one source IP (`203.0.113.10`) → **many different ports**, same target, in seconds.
**Verdict:** classic port scan — attacker is enumerating open services before deciding what to attack next.

> This is exactly what a tool like Nmap produces — `nmap -p- <target>` in a lab leaves this firewall-log signature on the receiving end.

---

## Scenario 2: Web Attack (WAF Logs)

    action=BLOCK request="GET /search.php?q=<script>alert('XSS')</script>" rule_id=941100 attack_type="XSS"
    action=BLOCK request="GET /../../../../etc/passwd" rule_id=930120 attack_type="Directory Traversal"

| Attack type | What it's doing |
|---|---|
| SQLi | Trying to dump/manipulate database contents via the query string |
| XSS | Injecting a script to run in another user's browser |
| Directory Traversal | Using `../../` to escape the web root and read arbitrary files (`/etc/passwd`) |

**Analyst move:** filter for `action=BLOCK` first — that's your signal, everything else is noise.
**Why WAF > plain firewall here:** a firewall log just says "allowed/blocked port 443." A WAF tells you *what kind* of attack was inside that HTTP request — the difference between "something happened" and "someone tried SQLi."
**Verdict:** high-confidence active attack against the web app, multiple techniques from the same actor.

---

## Scenario 3: VPN Brute-Force

    10:12:11 FAILED_AUTH ... (user 'admin')
    10:12:15 FAILED_AUTH ... (user 'admin')
    10:12:21 SUCCESS_AUTH ... 198.51.100.88 (user 'b.jones')
    10:12:08 FAILED_AUTH ... (user 'guest')

**Pattern:** one source IP → **massive FAILED_AUTH volume**, cycling common usernames (`admin`, `guest`, `user`, `root`). The odd `SUCCESS_AUTH` from a different IP is just a normal employee logging in.
**Analyst move:** group/filter by source IP, not by username — the attacker rotates usernames, not IPs, so the IP is the consistent signal.
**Verdict:** brute-force / credential-stuffing attempt against the VPN gateway.

---

## Pattern Recognition Cheat Sheet

| Pattern | Meaning |
|---|---|
| One source → many destination **ports** (same host) | Port scanning |
| One source → many destination **hosts** (same port) | Network sweep / scanning |
| One source → one destination, high volume | Brute-forcing |
| Traffic at perfectly regular intervals | Malware beaconing (C2 check-ins) |

**Why regular intervals matter:** humans and normal apps generate bursty, irregular traffic. A connection firing every exactly 60 seconds, forever, is a machine doing it — the regularity itself is the red flag, independent of destination or payload.

# Investigating a Full Attack Chain (Perimeter Logs Lab — Initech Corp)

**Core idea:** A compromise rarely shows up as one log line — it shows up as a *chain* across firewall → IDS → VPN logs, each stage handing you the pivot point (an IP) for the next.

## Asset Reference

| IP | Hostname | Role | OS | Criticality |
|---|---|---|---|---|
| 10.0.0.20 | FINANCE-SRV1 | File/Finance Server (SMB) | Windows Server | High |
| 10.0.0.50 | VPN-GW | VPN Gateway | Linux | Critical |
| 10.0.0.51 | APP-WEB-01 | Internal Web/App | Linux | High |
| 10.0.0.60 | WORKSTATION-60 | Employee Workstation | Windows 10 | Medium |
| 10.8.0.23 | VPN-CLIENT-ATTK | VPN-assigned client (ephemeral) | N/A | Critical |
| 10.0.1.10 | DMZ-WEB | DMZ Web Server | Linux | Medium |

**Why this table matters:** without it, `10.0.0.50` is just a number. With it, "attacker hitting 10.0.0.50" instantly reads as "attacker going after the VPN gateway" — the most critical asset. Asset context turns a log line into a priority decision.

## Tooling
Manual CLI (`grep`/`cut`/`sort`/`uniq`) vs. Splunk — this walkthrough uses manual CLI because it forces actual understanding of what you're filtering for.

## Stage 1 — Reconnaissance (Port Scanning)

    cat firewall.log | grep "BLOCK" | head

Shows one external IP hitting multiple internal ports (21, 22, 23, 445, 3389) — a scan signature.

Find who's most persistent:

    cat firewall.log | grep "BLOCK" | cut -d' ' -f5 | cut -d: -f1 | sort -nr | uniq -c

`cut -d' ' -f5` grabs source IP:port; `cut -d: -f1` strips the port; `sort | uniq -c` counts per IP — top count = prime suspect.

Check if that IP got anything through:

    cat firewall.log | grep [SUSPICIOUS_IP] | grep "ALLOW"

Some connections were allowed despite the scanning — meaning the attacker eventually got in. Pivot from "attacker outside" to "attacker has a foothold."

## Stage 2 — Initial Access (VPN Brute-Force)

    cat vpn_auth.log | grep FAIL | cut -d' ' -f3 | sort -nr | uniq -c

One IP dominates the failure count — classic brute-force signature.

    cat vpn_auth.log | grep [SUSPICIOUS_IP]

Rapid `FAIL` burst against one service account (`svc_...`), then `SUCCESS`. The log gives an `assigned_ip` (internal `10.8.0.x`) — **this is your new pivot**, since the attacker now operates from inside under this identity.

> **Why service accounts get targeted:** over-privileged, rarely monitored, weak static passwords set once at provisioning. Brute-forcing `svc_` accounts is a real-world TTP, not a lab coincidence.

## Stage 3 — Lateral Movement

    cat firewall.log | grep [COMPROMISED_IP] | grep "ALLOW" | head

Compromised host probing other internal machines on SSH/SMB/RDP (22/445/3389) — the classic "move to another machine" trio.

    cat ids_alerts.log | grep [COMPROMISED_IP] | head

Confirms `ET EXPLOIT` alerts — SSH scan, RDP brute-force, and an **MS-SMB Lateral Movement** alert.

    cat ids_alerts.log | grep -n [COMPROMISED_IP] | grep 'SMB' | cut -d' ' -f6,7,8,9,10,19,21 | head

Multiple SMB Lateral Movement hits confirm the attacker used SMB (PsExec/EternalBlue-style) to jump hosts.

## Stage 4 — Command & Control (C2) Beaconing

    cat ids_alerts.log | grep C2 | head

Repeated `ET TROJAN Possible C2 Beaconing` alerts, all to one external IP on port **4444** (classic Metasploit/reverse-shell default — recognize this on sight).

**The tell is the timing, not just the alert.** Timestamps land exactly 6 hours apart every time — no human browses on a perfect clock. This is the "regular interval = beaconing" pattern from the previous note, now seen in real data.

    cat ids_alerts.log | grep -n [COMPROMISED_IP] | cut -d' ' -f6,7,8,9,10,19,22,23 | uniq -c | sort -nr | head

C2 Beaconing alerts dominate — host is a confirmed active C2 implant.

## Stage 5 — Data Exfiltration

    cat firewall.log | grep [COMPROMISED_IP] | cut -d' ' -f5,6,7 | uniq | sort

Sustained high-volume traffic to an external IP on ports 80/8080 — exfil disguised as normal web traffic (rarely blocked outbound, blends in).

    cat ids_alerts.log | grep [COMPROMISED_IP] | tail

`ET INFO Possible HTTP POST Large Upload — Potential Data Exfiltration`, repeated and regularly timed. Combined with the C2 finding: full chain confirmed.

## Full Attack Chain Summary

| Stage | Log Source | Finding |
|---|---|---|
| Recon | firewall.log (BLOCK) | External IP port-scanning internal hosts |
| Initial Access | vpn_auth.log | Brute-forced `svc_` account, got internal IP |
| Lateral Movement | firewall.log + ids_alerts.log | SMB exploit used to pivot to another host |
| C2 | ids_alerts.log | Regular 6-hr beacons to external IP:4444 |
| Exfiltration | firewall.log + ids_alerts.log | Large HTTP POSTs to external IP over 80/8080 |

## Key Investigative Technique (reusable pattern)
1. Find the anomaly (high BLOCK/FAIL count) → identify suspect IP
2. Pivot: search all logs for that IP
3. Each stage's output gives you a **new IP** (or new host) to pivot on next
4. Repeat until the chain runs cold

This pivot-and-correlate loop across firewall → IDS → VPN logs *is* the actual job — memorize the loop, not just this specific example.
